**位置**：`D:\SoftWare\Develope\DshWorkPath\mo工具\ToolsChain\w64devkit`

| 项 | 值 |
|---|---|
| 编译器 | `bin\g++.exe`（GCC 14.1.0，**32 位**） |
| 反汇编 | `bin\objdump.exe` |
| 目录大小 | 约 281 MB（`bin` 单独 34.7 MB） |

**⚠️ 工具链在非 ASCII 路径下会找不到自己的库**：

```
ld.exe: cannot find -lkernel32
```

本项目路径含中文（`mo工具`），所以：

- **每次编译前**要把工具链和源码**暂存到 `%TEMP%`（纯 ASCII）**，编译完再拷回
- `build.bat` 已实现这个逻辑：**默认直接走 staging**（因为本项目路径必然含中文），
  想原地构建就设 `EP_INPLACE=1`
- 从 `src\` 出发，工具链的正确相对路径是 **`..\..\ToolsChain\w64devkit`**
  （`%~dp0` = `<仓库根>\src\`，爬两层到工作区根 —— 仓库把项目提升为根之后从三层变成了两层）

> ⚠️ 1.0 时代这里写的是"自动检测路径是否纯 ASCII"，那行代码
> （`echo %SRCDIR% | findstr ...`）在中文路径下**会崩**，
> 而且 `build.bat` 的工具链路径与 robocopy 源目录都算错了 ——
> **它其实从未成功运行过**。详见 `04-踩坑记录.md` 第 17 条。
> 1.2 已重写并实测通过（编译 + 三个自检 + 产物可复现）。

**⚠️ `%TEMP%` 在不同会话/不同调用之间不保证相同**
（如 `C:\Users\MOONBA~1\AppData\Local\Temp\dsh-KOWogA\`）。
所以**不能假设上次暂存的工具链还在**，每次都要检查并按需重建。

**提速建议**（已向用户提过，尚未采纳）：把 `w64devkit` 另放一份到纯 ASCII 的固定路径
（如 `D:\w64devkit`），可免去每次拷贝。

### 推荐的编译命令

```powershell
$tc   = "D:\SoftWare\Develope\DshWorkPath\mo工具\ToolsChain\w64devkit"
$work = "$env:TEMP\ep_build"
$d    = "D:\SoftWare\Develope\DshWorkPath\mo工具\对方玩家异常操作检测"

if (-not (Test-Path "$work\toolchain\bin\g++.exe")) {
    robocopy $tc "$work\toolchain" /E /NFL /NDL /NJH /NJS /NP /R:0 /W:0 | Out-Null
}
New-Item -ItemType Directory -Force -Path "$work\out" | Out-Null
robocopy "$d\src" "$work\src" /E /NFL /NDL /NJH /NJS /NP /R:0 /W:0 | Out-Null

$env:PATH = "$work\toolchain\bin;$env:PATH"     # ★ 必须设 PATH，否则 gcc 找不到 as.exe
$gpp = "$work\toolchain\bin\g++.exe"
$a = @("-Wall","-O2","-shared","-fno-exceptions","-fno-rtti",
       "-o","$work\out\FairGuard.dll","$work\src\FairGuard.c",
       "-nostdlib","-lkernel32","-lgcc",
       "-Wl,--enable-stdcall-fixup","-Wl,--no-insert-timestamp","-Wl,--entry,_DllMain@12")
& $gpp @a

Copy-Item "$work\out\FairGuard.dll" "$d\FairGuard.dll" -Force
```

**要点**：
- **必须设 `$env:PATH`**，否则报 `cannot execute 'as'`
- `-Wall`（或 `-Wall -Wextra`）保持零警告
- `-Wl,--no-insert-timestamp` 把 PE 头的 `TimeDateStamp` 清零 ——
  **但产物整体仍然不是按位可复现的**，详见下面的"关于可复现构建"
- 用数组传参，不要用 `-Wl,...` 拼字符串（PowerShell 会因逗号断行）

### 关于可复现构建（⚠️ 1.1 实测修正了旧说法）

1.0 的文档写"`-Wl,--no-insert-timestamp` 让产物可复现（连编两次哈希一致）"。
**1.1 实测：不成立。** 证据：

| 实验 | 结果 |
|---|---|
| PE `TimeDateStamp` 字段 | `0x00000000` ✓ 选项确实生效 |
| **`.o` 目标文件**连编两次 | **哈希完全相同** ✓ 编译器是确定的 |
| **链接后的 DLL** 连编两次（同目录、同命令、隔 2 秒） | **哈希不同** ✗ 大小都是 34,399 字节，差异约 880 字节，遍布各节 |
| 加 `-frandom-seed=FairGuard` | 仍然不同 ✗ |

⇒ **不确定性来自链接器（ld），不是编译器** —— 怀疑是相同优先级的符号/section
在每次链接时排序不稳定，导致代码里的绝对地址整体位移。

**这意味着**：
- 文档与日志里出现的 `SHA256 前 16 位`，只能当作"**这一份产物**的指纹"，
  用来核对"别人给你的 DLL 是不是这一份"，**不能**当作"可从源码复现"的证明
- 想真正做可复现构建，需要进一步研究 ld 的排序行为
  （可先试 `-Wl,--sort-section=name`）—— **1.1 未做，因为与检测功能无关**

## 三、反汇编 gamemd.exe

```powershell
& "$env:TEMP\ep_build\toolchain\bin\objdump.exe" -d `
    --start-address=0x64C380 --stop-address=0x64C3E0 `
    "E:\RA2\Mental Omega\gamemd.exe"
```

**⚠️ 注意**：`objdump` 对 PE 的 `--start-address` 用的是**虚拟地址**（ImageBase 已是 `0x400000`），
直接写 `0x64C380` 即可。

**不要**试图用 `-b binary --adjust-vma` 那种方式（会失败）。
也不要用"文件偏移 = VA - ImageBase + 0x400"去手算（**PE 节的文件偏移不等于这个**，
我在早期因此得出过错误的字节）。

## 五、沙箱与文件操作注意

- 沙箱模式 `workspace-write`，只能写工作区
- **`E:` 盘可读不可写** —— 部署 DLL / 取日志都要用户手动做
- **`%TEMP%` 每次调用都新建**（见上）
- 游戏日志是 **GBK 编码**，`read` 工具会报 `invalid UTF-8`。
  读的时候用：

```powershell
[System.IO.File]::ReadAllText($path, [System.Text.Encoding]::GetEncoding(936))
```

- 如果日志被游戏占用，用共享模式打开：

```powershell
$fs = [System.IO.File]::Open($path,'Open','Read','ReadWrite')
$sr = New-Object System.IO.StreamReader($fs, [System.Text.Encoding]::GetEncoding(936))
$txt = $sr.ReadToEnd(); $sr.Close(); $fs.Close()
```
