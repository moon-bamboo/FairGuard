# 踩坑记录 —— 开工前必读

> 下面每一条都是**实际踩过的**。重蹈一次就要浪费一整轮实机测试（用户要手动打一局才能复现）。

---

## 1. ⚠️⚠️ 钩点不能用 `0x64C380`（函数入口）—— 实测必崩

`0x64C380` 是 `Execute_DoList` 的函数入口，看起来最理想，但它要覆盖 **10 字节**：

```
64c380: 83 ec 40              sub  $0x40,%esp        ┐
64c383: 53                    push %ebx              ├ 10 字节
64c384: 8b 1d 38 02 a8 00     mov  0xa80238,%ebx     ┘
```

**挂上去必崩**（纯原版 + MO 都一样），`except.txt` 铁证：

```
Access address: C35AE9F8 was read from.
Eip: 02A1002E   Ebx: 0000000A          ← EBX 正好等于覆盖长度 10
Bytes at CS:EIP: 8B 3D F8 E9 5A C3     ← 应该是 8B 3D F8 41 8B 00
```

trampoline 里那条"原指令副本"的地址字段是错的。

**已排除的原因**（不要重复怀疑）：
- 地址错 —— 反汇编逐字节吻合，`Execute_DoList` 内部就是读 `0x8b41f8`
- 与其他插件同地址冲突 —— 搜过 MO 的 `Ares.dll`/`cncnet5*.dll`/`AutoLoad_nolog.dll`
  和原版的全部 DLL 钩子表，该地址无人使用
- MOD 有关 —— 纯原版同样崩

**结论：放弃它**，改用 `0x64C38D`（**一条指令、6 字节、绝对寻址、不碰栈**）：

```
64c38d: 8b 3d f8 41 8b 00    mov  0x8b41f8,%edi
```

**经验**：Syringe 的跳回点是写死的 `钩点+5`，长覆盖只能靠"把覆盖区全填 NOP"兜住。
**能选单条指令就不要选多字节覆盖，尤其不要选含 `sub esp`/`push` 这种改栈指令的。**

## 2. ⚠️⚠️ 单机测试永远拿不到数据

单机时 `DoList.Count` **每帧都是 0**，`Execute_DoList` 被调用后立刻跳走。
（反汇编 `64c3a1: jle 0x64c40d`）

**那套事件队列只为网络同步存在，单机不产生 `EventClass`。**

浪费过一整轮：单机跑了一局、做了造建筑/装车等操作，得出的结论却是"队列一直空"。

**⇒ 验证必须在联机环境做。** 单机只能验证"探针活着"。

---

## 3. ⚠️⚠️ `DoList` 是环形队列，不能按 `i*111` 算地址

早期版本直接算 `0x8B4204 + i*111`，**漏了 `Head` 偏移与取模**，
读到的全是错位条目 —— 表现为"`Count` 明明大于 0，却一条未执行事件都找不到"。

正确写法：

```c
head = *(int*)(0x008B41F8 + 0x04);              /* Head @ +0x04 */
slot = ((unsigned)head + i) & (16384 - 1);
element = 0x008B4204 + slot * 111;
```

来源是 `Execute_DoList` 自己的代码（`add`/`and $0x3fff`/`lea` 三连）。

## 4. `.inj` 必须是纯 ASCII

Syringe 按 ANSI 解析这个文件。曾经在里面写中文注释，
结果文件带上 **787 个非 ASCII 字节**。**注释一律用英文。**

构建后建议校验一次：

```powershell
$b = [System.IO.File]::ReadAllBytes("FairGuard.dll.inj")
($b | Where-Object { $_ -gt 127 }).Count   # 必须是 0
```

## 5. 日志正文必须用英文

源码是 UTF-8，而日志按 GBK 写（`LogUtf8=0`），**中文会变成乱码**
（实测出现过 `list: DoList 涓虹┖`）。

**约定**：日志正文用英文；中文注释留在 `.ini` 和文档里。

---

## 6. 一次启动会生成两个日志（已修）

Syringe 会在**自己的进程**里先调用一次 `SyringeHandshake`
（就是日志里 `Calling xxx.dll ... Answers ...` 那几行），握手会走到初始化并建日志 ——
于是每次启动都多出一个只有启动头的空日志。

- 344 字节（无 `frame alive`）= **Syringe 进程**
- 407/476 字节（有 `frame alive`）= **gamemd 进程** ✓

**修法**：建日志前判断宿主进程名是不是 `gamemd.exe`，不是就静默。

## 7. 缓冲边界：`UtoA`/`HtoA` 不做边界检查

这两个函数"只负责把自己那几位写出来"，**调用方必须先留足空间**：

- `AppNum()` 里先 `if (d + 14 > end) return end;`
- `HtoA` 会写 2 位十六进制 + 1 个 `'\0'`，追加前先确认放得下
- `HtoA` **必须补 `'\0'`**：有些调用点把它写的临时数组当字符串追加，
  没有终止符就会读到栈上的垃圾（实测出现过
  `DoList=<=1 DumpR008B41F8C:\Users...` 这种乱码）

---

## 8. 诊断信息不要采用"只在状态变化时记录"的写法

早期版本把"队列为空"的日志设计成**只在第一次记一行**，结果一局下来
只有初始化那一行，**完全看不出后面到底是持续为空、还是某个时刻有过内容**。

**改成定期汇报**（每 60 帧无条件记一行）之后，一眼就定位到了问题。

**经验**：诊断日志的**目的是让人看清过程**，"省日志"的优化在这里是反效果。

---

## 9. 不要想当然判断"哪个房号是本机"

第一次联机分析时，我因为"`h1` 几乎每帧都有一条 `FrameInfo`"就断定 `h1` 是本机，
**结论正好相反** —— 用户的操作全部记在 `h0` 名下。

**教训**：房号与本机的对应关系**从数据里验证**（比如让操作方做一个明确动作，
看哪个房号出现峰值），不要靠"哪边消息多"来推断。

---

## 10. 不要在数据不足时硬下结论

曾经把 `Move ×10` 判定为"自动装车的特征"，并据此提出判据。
**用户直接纠正**：那是他自己"放出单位后命令它们移动一下"的习惯操作。

**教训**：
- 用户的操作序列是**重要的先验信息**，分析前先问清楚、或让它与时间轴对齐
- 一批相同类型的命令**不足以定性**，要看更深一层的字段（如 `Destination`）
- 用户的直觉往往是对的（他说"这不符合我说的执行顺序"），认真对待

## 11. 探针装在"旁观者"位置时数据更完整

本机记录的 `Destination` 等字段**是空的**（事件刚生成时还没算出来）；
**对手那台的日志里字段是完整的**。

**⇒ 分析优先用对手日志。** 这也顺带说明：将来做"多方交叉验证"时，
**只能对事件头部（`+0..+12`）做哈希**。

## 12. 构建相关

- **32 位 gcc 在非 ASCII 路径下会找不到自己的库**
  （`ld.exe: cannot find -lkernel32`）—— 本项目目录名是中文，
  所以 `build.bat` 必须把工具链与源码**暂存到 `%TEMP%`（纯 ASCII）**再编译，然后拷回。
- `%TEMP%` 每次工具调用都会新建一个带随机后缀的目录
  （如 `...\Temp\dsh-KOWogA\`），所以**不能指望上次暂存的工具链还在**，
  每次都要检查/重建。
- **沙箱不允许往 `%TEMP%` 的固定子目录写**（实测 `C:\Users\...\Temp\ep_build`
  被 `Access denied`），也不允许 `subst` 把中文路径映射成 ASCII 盘符
  （`Access denied`）。所以只能"一次调用里拷工具链 + 编译 + 测试 + 拷回"。
  - 提速：`robocopy ... /XD share src` 可少拷约 35MB（`share` 用不到）
- 详见 `05-环境与工具.md`。

## 13. ⚠️ 测函数指针的调用约定时，必须**防止编译器内联**

写 `test/test_abi.c` 验证"用 `__fastcall` 表达引擎 `__thiscall`"是否正确时，
第一次跑 **-O2 报告失败**，改 **-O0 全部通过** —— 一度以为调用约定真的有问题。

**真正的原因**：测试里 `FakeAddMessage` 是 `static` 且地址就在同一个文件，
GCC 在 -O2 下把这次间接调用**去虚拟化并内联**了，于是"调用约定"被编译器顺手抹平，
测出来的东西跟 ABI 无关。

**修法**（两条都要）：

```c
static int __attribute__((thiscall, noinline)) FakeAddMessage(...);

/* 经 volatile 全局函数指针取出：真实插件里目标是引擎的固定地址，
   编译器不可能知道它是什么，所以测试也不该让它知道 */
static AddMessageFn volatile g_fnPtr = (AddMessageFn)(void*)FakeAddMessage;
```

**通用教训**：任何"验证 ABI / 调用约定 / 栈布局"的测试，
都要让被调方对编译器**不可见**（`noinline` + volatile 指针，或放另一个编译单元）。
否则测试会恒真、或给出误导性的失败。

## 14. ⚠️ 读反汇编核对参数位置时：`ESP+0` 才是第一个栈参数

核对 `FairGuard.dll` 里 `AddMessage` 的调用现场时，看到：

```
movl $0x0,(%esp)        <- 这是第 1 个栈参数
movl $0x0,0x4(%esp)     <- 第 2 个
mov  %esi,0x8(%esp)     <- 第 3 个
...
sub  $0x1c,%esp         <- 被调方 ret $0x1C 之后，调用方减回来
```

我一开始按"`+0x04` 是第一个参数（以为 `(%esp)` 是返回地址）"去对，
结论变成"参数整体错位、少了一个"，差点去改一段**本来就正确**的代码。

**正确读法**：`call` 执行时才把返回地址压到 `ESP-4`。
所以**调用前靠 `call` 那条指令的现场**里，`ESP+0` 就是第一个栈参数，
`call` 之后返回地址才占 `ESP+0`。

**结论（已用反汇编 + `test_abi.c` 双重确认）**：
`ECX = this`、7 个栈参数顺序正确、`ret $0x1C` 与调用方的 `sub $0x1c` 平衡 —— 全部符合。

## 15. 头文件里的大段注释中**不要嵌 `/* */`**

`engine_abi.h` 顶部那段说明里写了

```
 *     (this_ /*ECX*/, edxUnused /*EDX 占位*/, 再 7 个栈参数)
```

C 的块注释**不能嵌套**：第一个 `*/` 就把外层注释提前结束了，
后面的说明文字全被当成代码，编译报一堆莫名其妙的错。

**改法**：注释里要提到值时用 `[ECX]`、`(ECX)` 之类，别用 `/*...*/`。

（本项目的注释极多，写的时候顺手检查一下。）

## 17. ⚠️⚠️ `build.bat` 必须纯 ASCII，而且它原来根本跑不起来

1.1 时第一次调用 `build.bat`，报的错却是

```
'"D:\...\FairGuard\src\src"' is not recognized as an internal or external command
'��目的目录名是中文' is not recognized as an internal or external command
```

看着像路径问题，其实是**三件事叠在一起**：

### (a) 批处理文件里的中文注释会被 cmd 误解析

cmd.exe 按**本地 ANSI 代码页（中文 Windows 上是 GBK）**读取 `.bat`。
而文件是 UTF-8 —— 中文注释的字节按 GBK 解出来是乱码，
乱码里可能带 `|`、`&`、`>` 等字符，于是**注释行会"吃掉"或改写下一行命令**。

⇒ **和 `.inj` 同一条规矩：`build.bat` 一律不写中文注释。**
（源代码 `.c/.h` 是 UTF-8 中文注释，没问题 —— 编译器按 `-finput-charset` 处理。）

### (b) 工具链路径算错了

`%~dp0` 是**脚本所在目录**（`...\FairGuard\src\`），而工具链在工作区根：

```
%~dp0..\ToolsChain\w64devkit                  -> ...\FairGuard\ToolsChain\...   ✗ 不存在
%~dp0..\..\..\ToolsChain\w64devkit            -> <工作区>\ToolsChain\w64devkit    ✓
```

### (c) robocopy 的源目录多拼了一个 `src`

```bat
robocopy "%~dp0src" ...      rem  %~dp0 末尾已经带反斜杠 -> ...\src\src  ✗
robocopy "%~dp0."   ...      rem  正解
```

**这三条合起来意味着：1.1 之前的 `build.bat` 从未成功运行过。**
文档里那句"build.bat 已实现 staging 逻辑"是照着代码写的，没有实测。

⇒ **教训：构建脚本必须真的跑一遍，再写进文档。**

### (d) 顺带：不要在批处理里用管道处理"含中文的路径字符串"

原本有一行"自动判断路径是否纯 ASCII"：

```bat
echo %SRCDIR% | findstr /r /c:"^[ -~]*$" >nul || set "ASCII_OK=0"
```

它会挂，报 `... was unexpected at this time.`。
原因：**GBK 双字节的第二字节范围是 0x40–0xFE，其中就包含 `|`(0x7C) 和 `>`(0x3E)** ——
路径里的中文展开之后，cmd 在管道解析阶段看到了一个"凭空多出来的管道符"。

⇒ 现在改成**默认直接走 staging**（本项目路径必然含中文），
想要原地构建就设 `EP_INPLACE=1`；不再做那个自动判断。

## 18. `%TEMP%` 在本次会话里是**固定**的，但仍不要依赖它

1.0 时代的记录说"每次工具调用都会新建一个带随机后缀的目录"。
本次实测：同一会话内 `$env:TEMP` 始终是 `...\Temp\dsh-EUGPyi`，
但**仍然不要在两次调用之间指望它**（换个会话就变了，而且换机器更没有保证）。

沙箱另外还拒绝了两件事（都试过）：

- 往 `%TEMP%` 的**父目录**下建固定目录：`Access to the path 'ep_build' is denied`
- `subst X: <中文路径>` 做 ASCII 盘符映射：`Access denied - D:\...\mo????`

⇒ 可行的做法只有：**一次调用里拷工具链 + 编译 + 测试 + 拷回**。
`build.bat` 就是这个流程（用户手动跑时不受沙箱限制，但保持同一流程）。

## 19. `--no-insert-timestamp` **不**等于"可复现构建"

1.0 文档里写着"`-Wl,--no-insert-timestamp` 让产物可复现（连编两次哈希一致）"。
写文档 07 时顺手核对了一下产物指纹，发现**每次编译出来的 DLL 哈希都不一样**，
于是做了一遍 A/B：

| 实验 | 结果 |
|---|---|
| PE 头 `TimeDateStamp` | `0x00000000` ✓（选项确实生效） |
| `.o` 连编两次 | **完全相同** ✓ |
| DLL 连编两次（同目录同命令，隔 2 秒） | **不同**，大小都是 34,399 字节，差异约 880 字节、遍布各节 |
| 再加 `-frandom-seed=FairGuard` | 仍然不同 |

⇒ **不确定性在链接器（ld），不在编译器。**
（`.o` 确定，DLL 不确定 —— 这条对比是判断"谁的锅"的最快办法。）

**对文档的影响**：日志、README 里的 `SHA256 前 16 位` 只能当
"**这一份产物**的指纹"（核对别人给的 DLL 用），**不能**当成"源码可复现"的证明。
详见 `05-环境与工具.md` 的"关于可复现构建"。

**顺带一个教训**：1.0 时"连编两次哈希一致"这句话从来没有被实测过，
是**照着编译选项想当然写下的**。凡是写进文档的性能/属性断言，
至少要跑一次 A/B —— 这次就是靠 A/B 才发现的。

## 20. ⚠️ `if (...)` 块里的 `echo` 文本**不能含未转义的 `)`**

`build.bat` 里有一行

```bat
    echo       copying toolchain (about 250MB, please wait)...
```

它在 `if ... ( ... ) else ( ... )` 的括号块内。cmd 解析时把 `250MB)` 的 `)` 当成
**块的结束**，于是后面的 `set "WORK=..."`、`robocopy ...` 全被踢出块外，
表现成"执行到 [2/5] 就报 `... was unexpected at this time.`"，
而且 `echo on` 追踪里能看到命令条数莫名其妙地少了几行。

**修法**：块内 echo 一律避开括号（或者写成 `^(` `^)`）：

```bat
    echo       copying toolchain - about 250MB, please wait...
```

**怎么最快定位这类问题**：把 `@echo off` 换成 `@echo on` 存成临时副本再跑，
对比"应该执行的命令"和"实际执行的命令"，一眼就能看出块在哪里被截断。

## 21. ⚠️⚠️ 同一个字段，在不同 Mission 下**语义不同** —— 判据必须有 Mission 前提

**这是 1.2 修掉的那个误报，也是最值得记住的一条。**

1.1 的判据是"对所有 `MegaMission` 统计 `Destination` 的不同取值个数"。
用户实测"选中 20 个单位、进入路径点模式、移动到某个点" → **整批误报**。

日志铁证：那一局 20 次命中**无一例外 `Enter=0`**（`Move=20` 或 `Other=20`）。

**原因**：`Destination` 这个字段的含义**取决于 Mission**：

| Mission | 目标是什么 | Destination 表现 |
|---|---|---|
| `2` Move | 一个**格子** | 路径点模式下引擎给**每个单位**展开各自的目标格 → 天然分散（20 个单位 → 10~14 个值） |
| `7` Enter | 一辆**载具本体** | 手动点同一辆车恒为 1；自动装车 10 配 10 → 10 |

**于是"20 个单位、Destination 有 10 个不同值"这件事**：
- 在 Move 下是**完全正常的**（引擎的路径规划，与手速无关）
- 在 Enter 下才是**人手做不到的**（要点中 10 辆不同的车）

**教训（可以推广）**：
1. **一个字段的含义要连着它的上下文（这里就是 Mission）一起验证**，
   不能因为"在某一类样本上对得上"就当成通用规律。
   1.0 时代的字段校准只用了 `Enter` 的样本（文档 03 那张表全是 `07xN`），
   却把结论推广到了所有 MegaMission —— 这就是错误来源。
2. **误报发生后，第一件事是看"所有误报有没有共同特征"**。
   这次 20 条全是 `Enter=0` —— 一眼就能看出问题在 Mission 上。
   如果只盯着 `veh` 数字调阈值，会越调越糟（放宽就误报、收紧就漏报）。
3. `Destination` 里那两个字节的 **RTTI**（`0x0B`/`0x34` 之类）至今没深究，
   但**不影响结论** —— 不过这也提醒：这个字段还有没搞清的部分。

**修法**：`MissionFilter`（默认 `7`），并写了
`case_pathway_move_false_positive()` 把"旧行为确实会误报"固化成回归用例，
免得以后有人"顺手"把默认值改回 0。

## 22. 用户的日志在 `E:` 盘上**读得到** —— 别让用户手抄

本项目文档一直写着"`E:` 盘只读、取日志要用户手动操作"。**"只读"是"不能写"，
不是"不能读"**。1.2 开发时直接读了：

E:\RA2\Mental Omega\MsgLog\EventProbe_2026-10-05_20-17-34.log   (2.1 MB / 32,173 行)

而在此之前我的推测方向（编队移动、阈值）**全都是错的**。

## 23. 项目改名要连"标识符"一起改，而不只是文件夹名

`EventProbe` → `FairGuard` 涉及的远不止目录名：

| 类别 | 要改的东西 |
|---|---|
| 目录 / 文件名 | 目录、`FairGuard.dll`、`FairGuard.ini`、`FairGuard.dll.inj`、`src/FairGuard.c` |
| 导出符号 | `FairGuard_ExecuteEventsHook`、`FairGuard_FrameHook`（**`.inj` 里引用的名字必须同步**） |
| 配置段 | `[EventProbe]` → `[Probe]`（**代码里的 `GetPrivateProfile*` 段名也要改**） |
| 日志/文件路径 | `MsgLog\FairGuard_*.log`、`FairGuard.ini` |
| 头文件宏 | `EVENTPROBE_*_H` → `FAIRGUARD_*_H` |
| 文档 | 全篇 |

**两个坑**：
1. **`.inj` 里的函数名和 DLL 导出名必须逐字一致** —— 改了 DLL 不改 `.inj`，
   游戏一启动就找不到钩子函数（Syringe 会报错或静默失败）。
2. **`Move-Item` 移动目录会被沙箱拒绝**（`Access to the path ... is denied`），
   但 `robocopy /E /MOVE` 可以（`exit=1` 表示有文件被复制，是**正常**返回码）。

**验证办法**：改完之后全项目 grep 一遍旧名字，
**例外只有历史日志**（`报错日志/`、`实测样本-*.txt`）—— 那些是历史事实，不该改。

## 24. ⚠️⚠️ 破坏性清理**绝不能**放在"可能失败"的分支里（本次真删了东西）

发布准备时要把项目从 `FairGuard/` 提升到仓库根。我写了一个循环，
逐个 `git mv` 顶层条目，**然后在循环后面跟了一句清理**：

```powershell
foreach ($i in (Get-ChildItem "$repo\FairGuard" -Force)) {
  git mv "FairGuard/$($i.Name)" "$($i.Name)"      # 目录级重命名会被系统拒绝
}
Remove-Item "$repo\FairGuard" -Force -Recurse      # ← 无条件执行，这里出了事
```

`git mv` 对**目录**报 `Permission denied`（见下一条），于是：
- `开发文档/` 没被移走
- 但 `Remove-Item` 照常执行了，**删掉了 10 个文档 + 13 个归档文件**

**为什么没造成损失**：这些文件都已经提交过，
`git checkout HEAD -- "FairGuard/开发文档" "_archive"` 一条命令全部恢复。

**但**：当时刚写好、还没提交的 `LICENSE` / `CHANGELOG.md` / `DISCLAIMER.md`
**没有这层保护，直接没了**，只能重做（LICENSE 重新从 gnu.org 取了一遍）。

**教训（两条，都很硬）**：

1. **清理动作必须放在"确认前置步骤全部成功"之后**，
   而不是无条件跟在循环后面。正确写法是检查返回值、或者先验证目标就位：

   ```powershell
   # 先确认目标确实有内容，再删源
   if ((Get-ChildItem $dst -Recurse -File).Count -eq $expected) { Remove-Item $src -Recurse }
   ```

2. **"提交留档"是真的能救命的**。这次能零损失恢复，完全是因为
   用户要求"关键节点提交"。**新写的东西要么尽快提交，要么别用递归删除碰它。**

## 25. 目录级重命名在本环境会被拒绝 —— 只有 `robocopy /MOVE` 可行

想把 `FairGuard/开发文档/` 整体移到上一级，试过：

| 办法 | 结果 |
|---|---|
| `git mv FairGuard/开发文档 开发文档` | `fatal: renaming ... failed: Permission denied` |
| `[System.IO.Directory]::Move(...)` | `Access to the path ... is denied` |
| `Move-Item` | `Access to the path ... is denied` |
| `cmd /c rd /s /q` | `The process cannot access the file because it is being used by another process` |
| **`robocopy <src> <dst> /E /MOVE`** | ✅ **可以** |

`robocopy` 的返回码 **1 = 有文件被复制，是成功的**（只有 ≥8 才算失败），
别把它当错误。

**推论**：**文件级**移动是允许的（`git mv 单文件`、`Move-Item 单文件` 都正常），
只有**目录级**操作会被挡。所以重排目录时要么逐文件搬，要么用 robocopy。
另外空目录可能因为"被进程占用"删不掉 —— 但 **git 不跟踪空目录**，留着无害。

## 26. ⚠️ 改哈希链 = 改协议，老日志会**全部**校验失败

1.3 把哈希链的算法整个换掉了（原因见 `07` 第十节：旧算法混进了日志里没记录的数据，
导致谁都校验不了）。后果是：

> **1.0 ~ 1.2 的日志，用 1.3 的工具校验一定会在第 1 条就失败。**

这不是 bug，但**如果不在工具里区分版本，用户会以为自己的日志被人改了** ——
那是纯粹的误导。所以 `FairGuardReport` 会读日志里的版本号，
对 1.2 及更早的日志显示：

> "这份日志来自 1.2 或更早，哈希链无法用本工具校验……**这并不表示日志被篡改**"

**教训**：凡是"改变了输出格式/协议"的改动，**必须同时处理"旧格式怎么办"**。
要么兼容读，要么明确拒绝并说明原因 —— 最糟的是"看起来能读，结论是错的"。

**要做这种事的时候**：
1. 算法**抽成共用头文件**（`src/hashchain.h`），插件与校验工具 include 同一份 ——
   "两边各抄一份"是这类协议最大的坑
2. 界面上**按版本分流**，不要给出误导性的结论
3. 在 `CHANGELOG.md` 的"不兼容"一节里写明

## 27. 文档里的"精确数字"必然会过期 —— 用脚本审，别靠自觉

文档里原来写着 `FairGuard.dll（37,005 字节）` 这类精确值。 <!-- check-docs:ignore 这一行是历史叙述 -->
问题是**链接器不可复现**（见第 19 条），每次编译字节数都不同 ——
这个数字从写下的那一刻就开始腐烂。

类似的还有：版本号（改一次要改一堆文档）、自检项数、文档里引用的文件路径
（目录一重排就全失效）。

**处理办法**：写了 `tools/check_docs.ps1`，把这些"会被改动的数字与路径"
抽出来自动核对，提交前跑一遍：

```
powershell -NoProfile -ExecutionPolicy Bypass -File tools\check_docs.ps1
```

它会检查：版本号（源码 vs 文档）、自检项数、**有没有把编译产物字节数写死**、
文档引用的项目文件是否存在、ini 键与代码是否对得上、`.bat` 是否纯 ASCII、
产物有没有误入 git。

**原则**：
- **会变的数字**（产物大小）→ 写成范围（"约 35 KB"）或干脆不写
- **能自动核对的东西**（版本号、项数、路径）→ 交给脚本
- 脚本自己也要**排除历史快照**（`_archive/`），并且**排除对别的项目的引用**
  （文档里确实会提到 `RAReplayPlugin\src\...`、`ChatBox\src\...`，
  那不是本仓库的文件）
