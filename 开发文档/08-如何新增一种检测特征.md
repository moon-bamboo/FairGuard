# 如何新增一种检测特征（扩展指南）

> 写给后来的开发者。
>
> 本文说三件事：**这个工具能看见什么**、**加一种新特征的标准流程**，
> 以及**最大的那个坑**（1.1 → 1.2 就是栽在它上面）。
>
> 目标不是"教你写代码"，而是**让你别重蹈我们踩过的坑** ——
> 每一条都是真实代价换来的。

---

## 一、先认清边界：我们只能看见"命令队列"

数据源是引擎的**命令队列**（`DoList`，所有玩家待执行的操作，
含远程玩家同步过来的）。所以：

**能看见** —— 任何走命令队列的玩家操作：

| 事件类型 | 例子 |
|---|---|
| `MegaMission`(0x04) | 移动、攻击、进入载具/建筑 |
| `Place`(0x0B) | 放置建筑 |
| `Produce`(0x0E) / `Suspend` / `Abandon` | 生产队列 |
| `Repair`(0x15) / `Sell`(0x16) | 修理、变卖 |
| `Deploy`(0x09) / `Detonate`(0x0A) | 展开、引爆 |
| `Message`(0x1A) | 聊天 |

每条都带：**哪个玩家、目标帧号、类型、参数**（`Whom` / `Mission` / `Destination` …）。

**看不见**（这些**不经过**命令队列）：

- **视野类**：去迷雾、全图显示 —— 直接改本地渲染，不打命令
- **微操类**：自动散开、自动闪避、自动拉残血 —— 本地循环执行
- **数值类**：资源、血量、冷却 —— 直接改内存
- **UI 层**：界面伪装、假消息

**推论**：这个项目的天花板就是"命令队列里能看出什么"。
别指望把它做成通用反作弊 —— 那需要另一套完全不同的手段。

## 二、★ 判据必须是"逻辑必然"，不是"看起来像"

**这是整个项目最重要的一条经验。**

### 合格判据：这个行为**人手根本做不到**

> 例：同一帧内对**多辆不同载具**下发进入命令。
>
> 玩家要点出这个操作，得逐个点（点单位A → 点载具A → 点单位B → 点载具B…），
> 10 个单位配 10 辆车就是 20 次点击。而一帧只有约 1/60 秒。
> **所以"出现"即"异常"，不需要调阈值、不需要统计学习。**

### 不合格判据：这个行为"看起来像自动化"，但人手也能做到

> 反例：一帧内有 10 条移动命令 ——
> 框选 10 个单位点一下地面，就是 10 条。**完全正常。**

### 自检问题（每次定判据前都问一遍）

> **把阈值压到最低，一个正常玩家会不会中招？**
>
> - 如果"会" → 这不是逻辑必然，而是启发式。
>   要么放弃，要么**把误报场景全部写进回归测试**并明说风险。
> - 如果"不会，因为人手物理上做不到" → ✅ 合格。

## 三、⚠️⚠️ 最大的那个坑：同一个字段在不同 Mission 下**语义不同**

**1.1 就是因为不知道这条，把"路径点模式移动"整批报成了自动装车。**

`Destination` 这个字段：

| Mission | 目标是什么 | `Destination` 表现 |
|---|---|---|
| `2` Move | 一个**格子** | 普通移动时大家同格 → 1 个值；<br>**路径点模式下引擎会给每个单位展开各自的目标格** → 20 个单位给出 10~14 个值 |
| `7` Enter | 一辆**载具本体** | 手动点同一辆车（不管框多少单位）→ 1 个值；<br>自动装车 10 单位配 10 辆 → 10 个值 |

于是"20 个单位、10 个不同目的地"：
- 在 `Move` 下是**引擎的正常规划**，与作弊毫无关系
- 在 `Enter` 下才是**人手做不到的**

完整证据见 `03-实测数据与判据验证.md` 第八节，
原始日志行见 `实测样本-2026-10-05-2017.txt`。

### 给新特征的三条启示

1. **用某个字段之前，先问"它在这一类命令里的含义是什么"** ——
   不要因为"它在某类样本上对得上"就当通用规律
2. **字段校准的样本要覆盖所有会用到它的 Mission**。
   当年校准 `Destination` 时只用了手动装车的样本（全是 `Enter`），
   结论本身没错，错在**推广**到了所有 Mission
3. **能限定就限定**：`MissionFilter` 就是这个思路。
   宁可少报一类，也不要拿语义不明的数据下结论

## 四、标准流程（照这个走，别跳步）

### 第 1 步 · 用探针收数据，**别猜**

```ini
[Probe]
Enable=1
DumpRaw=1
DumpBytes=32
BurstOps=99          ; 先关掉告警，专心收数据
[Detector]
TraceAll=1           ; 把"规模达标但没命中"的帧也记下来
```

联机做**已知操作**：先**手动**做一遍，再用插件做一遍，**每次间隔 10 秒以上**
（方便在日志里按时间切开）。

> 用户（非程序员）愿意配合实测，而且他的操作记录很准 ——
> **先问清楚他做了什么，再去读日志**，比你自己猜快十倍。

### 第 2 步 · 从数据里读出"人手 vs 插件"的分界

对着 `raw` 行逐条比：**哪个字段在两组数据里不一样？**

找到那个字段，才算找到判据。找不到就说明这条路走不通 —— **如实说，别硬凑**。

### 第 3 步 · 把判据写成纯算法

在 `src/detector_core.h` 里加：

```c
/* ① DetStat 里加统计字段 */
int nXxx;

/* ② DetStat_Feed 里加采集分支（注意 Mission 过滤！） */
if (mission == DET_MISSION_XXX) s->nXxx++;

/* ③ 加判定函数（或扩展 DetStat_Judge） */
static inline int DetStat_JudgeXxx(const DetStat* s, const DetRule* r) { ... }
```

**关键：保持"不依赖任何引擎地址、可以离线单测"这个性质。**
这是这个项目能快速迭代、能放心改判据的原因（改了立刻跑 `test_detector` 就知道有没有崩）。

### 第 4 步 · ★ 必须配两类回归测试

在 `test/test_detector.c` 里加：

```c
/* 应该命中的（防漏报）*/
static void case_xxx_hit(void)
{
    ... 用插件的数据构造 ...
    check("xxx : IS a hit", DetStat_JudgeXxx(&s, &r) == 1);
}

/* 不该命中的（★ 防误报 —— 这一组更重要）*/
static void case_xxx_normal(void)
{
    ... 用**真实的正常操作数据**构造 ...
    check("xxx : NOT a hit", DetStat_JudgeXxx(&s, &r) == 0);
}
```

**防误报那一组必须用真实的正常操作数据**，不是你想象出来的"正常操作"。
已知的误报场景一律固化成用例 —— 1.2 修的那个误报就是这么防住的
（`case_pathway_move_false_positive()` 甚至把"旧行为确实会误报"也固定下来了，
防止以后有人把默认值改回去）。

### 第 5 步 · 接进主程序

`src/FairGuard.c` 里要动的地方：

| 位置 | 做什么 |
|---|---|
| `DetConfig` + `LoadConfig` + `EnsureInit` | 新配置项（记得加中文注释） |
| `OnDetectHit` 附近 | 新特征的告警日志行 |
| `PendingAlert` / `ShowPendingAlert` | 如果要弹屏幕提示（注意节流） |
| `ChainPush` | 如果新特征也要进哈希链 —— **⚠️ 那就是改协议**，见 `04` 第 26 条 |

### 第 6 步 · 文档与审计

- `FairGuard.ini`：配置项 + **中文注释**（写清"为什么"和**误报风险**）
- `开发文档/07`：新的日志行说明
- `CHANGELOG.md`：记一笔
- 跑 `tools/check_docs.ps1`（应为 exit 0）和 `src/build.bat`（应全绿）

## 五、值得做的扩展方向（按可行性 × 价值排）

### A. 同帧多建筑放置 / 多单位生产

- **现象**：一帧内多条 `Place`(0x0B) 且目标格各不相同；或多条 `Produce`(0x0E)
- **判据思路**：人手一次只能放一个建筑、点一次生产队列 ——
  同一帧多个**不同**目标 = 可疑（同 `Enter` 的逻辑）
- **前置工作**：先搞清 `Place` 的 `Destination` 语义
  （**很可能又是一个"同 Mission 语义坑"**，务必先收数据）
- **数据缺口**：目前 `evt` 行只给 `ops` 总数，需要先加**按事件类型的细分计数**

### B. 跨帧累积判据（对付"分帧下发"）

- **动机**：`07` 第 6.5 节的盲区 —— 插件每帧只装一辆车，单帧判据就失效了
  （1.2 复测时在 `trace` 行里就见过这种形态的可能迹象）
- **思路**：滑动窗口内统计"该玩家总共对多少辆**不同**载具下过进入命令"
- **难点（也是误报来源）**：要区分"一次点击产生的多辆车"和"多次点击"。
  可能的线索：**同一个 `Destination` 是否在多帧里反复出现**
  （重复下发同一目标是插件的特征，人不会这么点）
- **警告**：这条路**极易误报**，务必先收够正常玩家的数据再动阈值

### C. AI 房号自动识别

- 现在只能靠 `IgnoreHouses` 手工排除 AI
- 思路：AI 通常**没有 `OutList` 活动**（它不发送"本机操作"），
  可以用这一点自动区分 AI 与真人

### D. 更多"逻辑必然"型特征

需要先在数据里发现，例如：

- 同一帧内对**同一目标**下发互相矛盾的命令（进 A 又出 A）
- 极短窗口内的指令速率超过人类生理上限（**需要先有基线数据**，
  这类判据是启发式，不是逻辑必然 —— 谨慎）

## 六、明确**不做**的（项目边界）

| 不做的 | 原因 |
|---|---|
| **连点器 / 键盘宏** | 它们只是一辆一辆快速点，做不到同帧多目标；而且对 RTS 竞技**没有实质影响** ——「一键建造多个单位」已被玩家社区接受为正常功能（用户明确要求不纳入） |
| **判定"对方装了某个程序"** | 插件命令与手动命令**字节级同构**，仅凭数据做不到 |
| **视野 / 微操 / 数值类作弊** | 不经过命令队列，看不见 |
| **把结论当证据** | 见 `DISCLAIMER.md`：这是可疑度报告，不是判决书 |
