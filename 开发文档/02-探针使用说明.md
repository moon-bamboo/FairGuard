# 探针（诊断模式）—— 排查手册

> ## ⚠️ 先看这里
>
> **探针从 1.3 起默认是关闭的**（`FairGuard.ini` 里 `[Probe] Enable=0`）。
> 它不再是日常功能，而是一个**排查工具** —— 只有当你怀疑"是不是根本没取到数据"、
> 或者"某个字段解析错了"的时候才需要打开。
>

> | 判据为什么这么定、实测数据 | `03`、`00` 第四节 |

## 一、它和检测器的关系

同一个 DLL 里的两件事，**共用同一次取样**（钩子 `0x64C38D` + `0x55D360`）：

| | 检测器 `[Detector]` | 探针 `[Probe]` |
|---|---|---|
| 目的 | 实时抓自动装车（**正式功能**） | 看"引擎的事件队列里到底有没有东西" |
| 输出 | `DETECT` / `trace` / `alive` / 屏幕提示 | `evt` / `list` / `raw` / `BURST` |
| 默认 | 开 | **关** |

**为什么合成一个 DLL**：两者要钩同样的两个地址，而 Syringe 对**同一地址**的多次 hook
是后装覆盖先装 —— 两个 DLL 各钩一次，必然有一个哑掉甚至崩溃。

**为什么探针默认关**：实测一局 4.5 分钟的日志有 16,159 行 / 1 MB，
其中 **15,540 行（96%）是探针的 `evt` 行**。关掉后日志只剩告警与报活，约 1/25。

---

## 二、怎么打开

编辑 `FairGuard.ini`：

```ini
[Probe]
Enable=1          ; 打开探针（默认 0）
DumpRaw=1         ; 需要核对原始字节时再开（日志会变大）
LogEveryFrame=0   ; 想看"每帧都在跑"就设 1（能算帧率）
BurstOps=5        ; 命令量告警阈值；嫌吵就设 99
```

改完重启游戏生效。

## 三、探针专属的日志行

> 检测器自己的行（`DETECT` / `DETECT-REPEAT` / `trace` / `[DETECT] alive` / `DETECT-SUMMARY`）
> 在 **`07` 第五节**里讲，这里不重复。

### 3.1 `evt` 行 —— 每帧按玩家分桶的命令统计（有事件时才输出）

```
evt f=22364 q=14 n=11 | h0 ops=10 chat=0 proto=0 MM=10 | h1 ops=0 chat=0 proto=1
    │       │  │        │  │              │             └ 另一个玩家
    │       │  │        │  │              └ MegaMission 数量
    │       │  │        │  └ 玩家操作数
    │       │  │        └ 房号
    │       │  └ 本帧事件总数
    │       └ DoList 当前总条数（含未来帧，用来看积压）
    └ 逻辑帧号
```

| 字段 | 含义 |
|---|---|
| `ops` | 玩家操作类（移动/生产/建造/修理/卖…） |
| `chat` | 聊天 |
| `proto` | 协议类（`FrameInfo` 等 —— **每玩家每帧都有，不是操作**） |
| `other` | 其余（仅非零时显示） |
| `MM` | 其中 `MegaMission` 的数量 |

> ⚠️ `FrameInfo(0x1C)` 每个玩家每帧都发一条，不单独归类会淹没统计 ——
> 所以它被算进 `proto`。

### 3.2 `list` 行 —— 每 60 帧一次的队列状态（**不管有没有数据都记**）

```
list: f=1920 in=5/10 out=2/3 calls=959 maxOps=3@h0 | e0 t=1C h=1 fr=1920 ex=0
           │      │  │    │  │      │       │          │
           │      │  │    │  │      │       │          └ 首条事件：类型/房号/目标帧/已执行
           │      │  │    │  │      │       └ 历史最高 ops 出现在哪个房号
           │      │  │    │  │      └ 单帧单玩家 ops 的历史最大值
           │      │  │    │  └ 钩子累计调用次数
           │      │  │    └ OutList 当前 / 历史最大
           │      │  └ DoList 当前 / 历史最大
           │      └ 同上（当前值 / 历史最大值）
           └ 帧号
```

**这一行是定位"哪一步没东西"的关键**：

| 现象 | 含义 |
|---|---|
| `calls` 不增长 | 钩子所在函数压根没被调用 |
| `calls` 增长但 `in=0/0` | 事件队列一直是空的 → **单机就是这样**（见 `01` 第五节） |
| `in>0` 但没有 `evt` 行 | 帧号基准不对（曾经的环形索引 bug 就是这样） |
| `maxOut>0` 而 `maxIn=0` | 事件只停在"本机待发"，没进待执行队列 |

> 1.3 之后探针默认关，打开了才看得到这一行。
> **平时判断"有没有数据"用 `[DETECT] alive` 行的 `scans=`**（见 `07` 第 4.1 节）。

### 3.3 `raw` 行 —— 每条事件的原始字节（`DumpRaw=1` 时）

```
raw f=22364 h=0 t=0x04 fr=22364 ex=0 | 04 00 00 5C 57 00 00 6D 3E 10 00 34 02 06 ...
                                        ↑  ↑  ↑  └────┬────┘ └─────┬──────┘ ↑  ↑
                                      类型 执行 房号   Frame      Whom(5B)   Mission gap
```

**解析偏移**：`[0]`类型 `[1]`已执行 `[2]`房号 `[3..6]`帧号
`[7..11]`Whom `[12]`**Mission** `[13]`gap `[14..18]`Target `[19..23]`**Destination**

`DumpBytes` 控制每条 dump 多少字节（默认 32，最大 111）。

> 字段偏移已经在真实联机日志上校准过（`01` 第三节），平时不需要开这一项。

### 3.4 `BURST` 行 —— 探针层的**粗略**告警

```
*** BURST f=22364 h=0 ops=10  (MegaMission=10, Mission=7(Enter): 10)
```

单帧该房号的玩家操作数达到 `BurstOps` 就记一行。括号里是该房号自己的
`MegaMission` 数与其中 `Mission=07(Enter)` 的条数。

> ⚠️ **这不是判据** —— 它只看"命令条数多不多"，不看目的地，
> 正常玩家框选一批单位点一辆车也会触发。真正的判据是 `*** DETECT` 行。
>
> 留着它是因为它顺带给出了该房号的 MegaMission / Enter 计数 ——
> **1.2 定位那次漏报，正是靠这一行找到证据的**（见 `03` 第八节）。

## 四、排查流程

### 症状：日志里除了启动头什么都没有

1. 先看启动头有没有 `hook: frame alive` 和 `hook: ExecuteEventsHook #1 entered`
   - 没有 → DLL 没被加载，或钩子没挂上 → 看 Syringe 日志里有没有 `Recognized DLL`
2. 打开探针，看 `list:` 行：
   - `calls` 不增长 → 钩子所在函数没被调用
   - `calls` 增长但 `in=0/0` → **事件队列是空的**
     - **单机？** 单机不产生 `EventClass`，这是正常的（`01` 第五节）
     - 联机也这样？→ 地址可能不对（但 `0x008B41F8` 已多次实测）
3. 都没问题，就去看 `07` 第 4.1 节的 `scans=` —— 那才是检测器视角的活性指标

### 症状：怀疑字段解析错了

1. `[Probe] DumpRaw=1` + `DumpBytes=32`
2. 做一个**已知操作**（比如手动框选 5 个单位点一辆运输车）
3. 在日志里找对应时间点的 `raw` 行，按 3.3 的偏移人工核对：
   - `[12]` 应该是 `07`（Enter）
   - `[19..23]` 在那几条里应该**完全相同**（同一辆车）

## 五、历史：判据是被探针"校准"出来的（已完成，留档）

1.0 时代探针是**主力工具**，三阶段走完才敢写检测规则：

| 阶段 | 做了什么 | 结论去哪了 |
|---|---|---|
| 1. 单机校准 | 确认地址 / 结构 / 字段偏移 | `01-技术方案.md` |
| 2. 联机取样 | 确认**远程玩家的事件能看到**（整个方案的前提） | `03-实测数据与判据验证.md` |
| 3. 定阈值 | 手动操作 vs AutoLoad 的数据对照 | `00` 第四节的判据 |

**这三步的结论现在都固化在代码与文档里了**，所以探针从主力降级成了排查工具。
需要复现当时的流程时看 `03` 第七节。
