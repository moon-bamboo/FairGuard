# 检测器使用说明（抓"自动装车"）

> 这份是**给使用者看的**：怎么装、怎么确认它在工作、命中时看到什么、怎么调、怎么测。
> 原理与证据看 `00-项目总览.md` 第四节，实测原始数据看 `实测样本-2026-10-05-2017.txt`，
> 实现细节看 `06-下一步-检测器设计.md`。
>
> **当前版本 1.2** —— 针对第一轮实机测试暴露的误报/漏报做了修正，见第二节。

---

## 一、它做什么

在联机对局里**实时**发现对手用"自动装车"类插件，然后：

1. **屏幕上弹一句提示** —— 当场就能看到，不用等打完一局翻日志
2. **日志里记一行详情** —— 帧号、房号、几个单位配几辆不同载具
3. **带哈希链** —— 日志被事后改动会对不上（局限见第六节）

判据（**已由真实联机数据验证**）：

> 同一帧内、同一玩家的一批 **`Enter`（进入载具）** 命令里，
> **「目的地不同取值个数」** 达到 **`MinDest`（默认 3）** → 自动装车。

**为什么是"逻辑必然"**：让 10 个单位各进 10 辆**不同**载具，玩家必须逐个点
（点单位A → 点载具A → 点单位B → 点载具B……）共 20 次点击，
**人手不可能压进同一帧**（一帧约 1/60 秒）。插件一次下发就能。

## 二、⚠️ 1.2 的两处修正（都来自你第一轮测试的日志）

### 2.1 误报：路径点模式移动被报了

**你的操作**："选中 20 个单位，进入路径点模式，移动到某个点" → 弹出告警。

**日志证据**（`实测样本-2026-10-05-2017.txt`）：20 次命中**无一例外 `Enter=0`**

```
*** DETECT f=10321 h=0 units=20 veh=10 MM=20 (Move=20 Enter=0 Other=0)
*** DETECT f=13823 h=0 units=20 veh=14 MM=20 (Move=0  Enter=0 Other=20)
*** DETECT f=16943 h=0 units=20 veh=10 MM=20 (Move=20 Enter=0 Other=0)
```

**原因**：`Destination` 的语义**随 Mission 变化**

| Mission | 目标 | Destination |
|---|---|---|
| `2` Move | 一个**格子** | 路径点模式下引擎给每个单位展开**各自的目标格** → 天然分散（20 个单位 → 10~14 个值）→ **误报** |
| `7` Enter | 一辆**载具本体** | 手动点同一辆车 → 恒为 1；自动装车 10 配 10 → 10 ✓ |

**修正**：新增 `MissionFilter`，默认 `7` —— **只对 Enter 判定**。
`Move` 这类"目标不是具体对象"的命令根本不参与判据。

**代价（必须知道）**：如果某个插件改用 `Move` 装车，就抓不到它了。
实测那个插件（AutoLoad）走的是 `Enter`，所以默认取 7。

### 2.2 漏报：20 单位 + 3 辆载具没被报出来

**你的操作**："选中 20 个单位和三辆 6 容量的载具，使用自动装车" → 无提示。

**日志证据**：这类命令**确实发生了**（BURST 行里有真实的 Enter 计数）：

```
f=19309 ops=20 (MegaMission=20, Mission=7(Enter): 20)
f=19488 ops=20 (MegaMission=20, Mission=7(Enter): 20)
f=19815 ~ f=19861  连续 7 帧，每帧 12 条 Enter
```

**没报的原因**：`veh` 只有 3（3 辆载具），被两道条件挡住：
`MinDest=5`（3 < 5）和 `RatioPercent=50`（3/20 = 15% < 50%）。

**修正**：`MinDest` 5→3、`RatioPercent` 50→0（不检查比例）。
只判 Enter 之后比例条件已无必要 —— 人手没法在同一帧点中多个**不同**载具。

**⚠️ 但这一条还没被证实**：日志里 `f=19815~19861` 连续 7 帧、每帧 12 条 Enter，
看起来 AutoLoad 是**分帧下发**的。如果真是这样，**每一帧的 `veh` 可能只有 1~2**，
而"手动框选 12 个单位点一辆车"也是每帧 12 条 Enter、`veh=1` —— 两者在数据上无法区分。

⇒ 所以 1.2 加了 `TraceAll` 诊断行，**需要你复测一次才能定论**（步骤见第七节）。

## 三、部署

把这三个文件放进**游戏根目录**（`gamemd.exe` 所在的那一层）：

```
FairGuard.dll          <- 插件本体
FairGuard.dll.inj      <- 钩子声明（文件名必须与 DLL 完全一致）
FairGuard.ini          <- 配置
```

日志写在：

```
<游戏目录>\MsgLog\FairGuard_日期_时间.log
```

> ⚠️ **装之前先把旧的 `EventProbe.dll` / `EventProbe.dll.inj` / `EventProbe.ini` 删掉。**
> 两个 DLL 会钩同一批地址，同时留着必然有一个哑掉甚至崩溃。
>
> ⚠️ **只需要自己装**。对手不用装任何东西。
>
> ⚠️ 装了 **ChatBox** 的话，屏幕提示会显示在 ChatBox 的消息窗里；没装就显示在
> 原版消息区（和"结盟提示""快捷键提示"同一个位置）。

## 四、先确认它在工作

打开日志，**开头**应该有这几行：

```
FairGuard 1.3 start
config: Enable=0 DumpRaw=0 DumpBytes=32 BurstOps=5 LogEveryFrame=0
detector: Enable=1 MinEvents=5 MinDest=3 RatioPercent=0 MissionFilter=7 TraceAll=0
detector: ShowAlert=1 AlertSeconds=10 WindowFrames=600 WindowHits=2 HashChain=1 ...
addr: DoList=<008B41F8> OutList=<00A802C8> CurrentFrame=<00A8ED84> AddMessage=<005D3BA0>
hash-chain: sha256, initial=<64位十六进制> (each DETECT line carries chain=...)
```

再看有没有心跳：

```
hook: frame alive (0x55D360), CurrentFrame=...
hook: ExecuteEventsHook #1 entered, frame=0
```

| 现象 | 含义 |
|---|---|
| 连 `start` 都没有 | DLL 没被加载 → 看 Syringe 日志里有没有 `Recognized DLL` |
| 没有 `frame alive` | 帧钩子地址有问题（不太可能，那是多方共用的老钩点） |
| `config:` 那行 `Enable=0` | **正常** —— 探针默认关闭（日志小），不影响检测器 |
| `detector:` 那行 `Enable=0` | 检测器被配置关掉了，那才是问题 |
| `MissionFilter=0(all)` | 过滤被关掉了 —— 会重新出现"路径点移动"误报 |

### 4.1 判断"到底有没有取到数据"

**探针默认是关的**（`[Probe] Enable=0`），所以不再有每 60 帧一行的 `list:`。
改看这一行 —— **它是关掉探针后唯一的活性指标**：

```
[DETECT] alive f=12600 hits=5 scans=177 frames=12601 byHouse=h0:5 chain=... recs=5
```

| 字段 | 含义 |
|---|---|
| `scans=` | **取到过 MegaMission 的帧数** ← 看它 |
| `hits=` | 这一局累计命中次数 |
| `frames=` | 检测器跑过的帧数（应该和 `f=` 差不多） |

- **`scans` 在涨** = 事件队列有数据、检测器正常工作 ✓
- **`scans` 一直是 0**（连启动头之后什么都没有）= 根本没取到数据：
  - **单机？** 单机不产生事件队列，必须联机
  - 地址不对？（不太可能，`0x008B41F8` 已多次实测）
  - `list: f=... in=0/0` 这种行要打开探针才看得到 —— 见下

**要更细的诊断就把探针打开**（`[Probe] Enable=1`），那时会有：

```
list: f=1920 in=5/10 out=2/3 calls=959 maxOps=3@h0 | e0 t=1C h=1 fr=1920 ex=0
```

`in=` 是 DoList 当前条数（`5/10` = 当前 5、历史最大 10）。
**单机时 `in=0/0` 是正常的** —— 单机不产生事件队列。

## 五、命中 / 未命中时看到什么

### 5.1 屏幕提示

```
【可疑】检测到自动装车特征：房号1 第26004帧 10 个单位配 10 辆不同载具
```

同一房号在 `AlertThrottleSeconds`（默认 10 秒）内**只弹一次** ——
因为"装卸循环"那种情况会在几秒内命中几十次，不节流屏幕会一直刷。
**日志不受影响，每一次命中都照常记录。**

10 秒内在滑动窗口里再次命中时，提示会变成：

```
【可疑·重复】自动装车特征：房号1 第26548帧 10 个单位配 10 辆不同载具（2 次重复）
```

> `房号` 是引擎里的玩家槽位编号，**不一定**等于"玩家1/玩家2"，
> 哪个房号是哪台机器要从日志核对（别靠"谁消息多"猜 —— 这是踩过的坑）。

### 5.2 命中行

```
*** DETECT f=26004 h=1 units=10 veh=10 MM=10 (Move=0 Enter=10) ratio=100% chain=1A2B3C4D5E6F7081
*** DETECT-REPEAT f=26548 h=1 hitsInWindow=2/600 frames, totalHits=2
```

| 字段 | 含义 |
|---|---|
| `f=` | 逻辑帧号 |
| `h=` | 房号（哪个玩家） |
| `units=` | 这批命令涉及几个**不同**的发令单位 |
| **`veh=`** | 打给了几辆**不同**的载具 ← **判据的核心数字** |
| `MM=` | 本帧该房号**参与判定**的命令条数（已过 MissionFilter） |
| `(Move=/Enter=/Other=)` | Mission 分布（**全部**命令，不受过滤影响） |
| `ratio=` | `veh / units` 的百分比（100% = 严格一对一） |
| `filtered=` | 被 MissionFilter 挡掉的条数 |
| `invalid=` | 字段还没算出来的条数（本机事件就是这样） |
| `dup=` | 去重时遇到"已有值"的次数 —— **正常现象**，多个单位进同一辆车就是这样 |
| `OVF=` | 去重集合真的装不下了 —— 出现才说明数据异常 |
| `[repeated]` | 本帧同时升级为"重复命中" |
| `chain=` | 哈希链当前值前 8 字节 |

> ⚠️ 1.1 的日志里 `OVERFLOW=` 其实是在数"重复值"，数字很大但毫无意义；
> 1.2 拆成了 `dup=`（正常）和 `OVF=`（异常）。

### 5.3 未命中行（`TraceAll=1` 时）—— **排查漏报的关键**

```
trace f=13823 h=0 units=0 veh=0 MM=0 (Move=0 Enter=0 Other=20) ratio=0% filtered=20
```

| 看到什么 | 说明什么 |
|---|---|
| `filtered=` 等于命令总数 | 这批命令的 Mission 不在 `MissionFilter` 里。<br>如果确认那是装车操作 → 把 `MissionFilter` 改成 `2,7` 再试 |
| `veh=1`（或 2） | 目的地不够分散。可能是真手动操作，也可能是**插件分帧下发**（这时确实区分不了） |
| `veh>=3` 却没报 | 不该发生 —— 把日志发我，是 bug |

### 5.4 汇总行

```
[DETECT] alive f=24000 hits=2 scans=812 frames=24000 chain=1A2B3C4D byHouse=h1:2 recs=2
[DETECT-SUMMARY] ver=1.3 f=74000 hits=2 scans=1904 firstHit=26004 lastHit=26548 byHouse=h1:2 chain=<完整64位> recs=2
```

`scans=` 是"出现过 MegaMission 的帧数" —— **它不涨说明根本没有数据**（比如单机）。

### 5.5 原始字节（`LogRaw=1` 时）

```
detraw f=26004 h=1 i=0 | 04 00 01 94 65 00 00 6D 3E 10 00 34 07 06 00 00 00 00 00 1D DF 00 00 0B
```

每条 24 字节（覆盖到目的地），用来人工复核判据。

## 六、⚠️ 边界与局限

### 6.1 单机没有数据

单机时 `DoList.Count` 每帧都是 0 —— **必须联机**。

### 6.2 本机事件与对手事件的差别

实测：同一条事件在两台机器上偏移 13 起有差异。**对手的事件字段完整，一定能检测**；
本机自己的事件在取样瞬间部分字段可能还没填好。

⇒ **优先用"没有操作的那台"的日志**（数据质量更好）。

### 6.3 只能发现"行为异常"，不能证明"对方装了插件"

插件产生的命令与玩家点击产生的命令**字节级同构**（AutoLoad 的源码注释自己写明了）。
本工具输出的是**可疑度报告**，最终判断由人来做。

### 6.4 `MissionFilter` 是双刃剑

只判 `Enter` 挡住了误报，代价是**走 `Move` 实现的插件抓不到**。
这是一次有数据支撑的权衡，不是保守起见。

### 6.5 分帧下发可能抓不到

如果插件把 20 个单位分几帧、每帧只处理一辆车，那一帧看起来就和手动操作一样。
**这条还没有定论**（见 2.2），要靠 `TraceAll` 复测。

### 6.6 温和使用检测不到 / 可以规避

- 一秒装一次、慢慢的，与手速快的玩家无法区分
- 加随机延迟、改走别的命令路径，特征就没了
- 单帧只装 2 个以下，低于 `MinDest` 也不报

### 6.7 哈希链只防"事后修改"

- 防不住**整份重新生成**（算法公开、无密钥）
- **单人日志无法自证**，要成为证据需**多方交叉核对**
- 只对**事件头部 +0..+12** 做哈希（目的地之后两台机器不一样）

## 七、实机测试步骤（1.2 复测）

> ⚠️ 每一步之间**间隔 10 秒以上**，方便在日志里按时间切开。

### 阶段 A · 部署与确认（单机即可）

1. 把旧的 `EventProbe.*` 三个文件从游戏目录**删掉**
2. 放入 `FairGuard.dll` / `FairGuard.dll.inj` / `FairGuard.ini`
3. **配置里把 `TraceAll=1` 打开**（这一轮要看"没报出来的是什么样"）
4. 启动游戏，看日志开头有没有 `start` + `detector:` + `frame alive`
5. 单机时 `list:` 行显示 `in=0/0` 是**正常的**

### 阶段 B · 误报回归（联机，最重要）

**只有你操作**，依次做（每个动作隔 10 秒）：

| 编号 | 动作 | 期望 |
|---|---|---|
| **A** | **选中 20 个单位 → 路径点模式 → 移动到某个点**（上一轮误报的就是这个） | **一次 `DETECT` 都不该有** |
| **B** | 手动框选 20 个单位 → 点**一辆**运输车 | **不报** |
| **C** | 手动 PvP 技巧：进载具A + 路径点 + 进载具B | **不报** |
| **D** | 框选 5 个单位 → 点地面普通移动 | **不报** |

A 是关键：它上次误报，这次必须干净。

### 阶段 C · 漏报回归（联机）

让**对手那台**装上 AutoLoad（或两台都装、你看对手的房号）：

| 编号 | 动作 | 期望 |
|---|---|---|
| **E** | 选中 **20 个单位 + 3 辆 6 容量载具**，按 **Ctrl+D**，等 10 秒 | 出现 `*** DETECT ... veh=3 ...` |
| **F** | 选中 **10 个单位 + 10 辆载具**，按 **Ctrl+D**，等 10 秒 | 出现 `units=10 veh=10` |
| **G** | 重复 2~3 次，每次隔 10 秒 | 第 2 次起有 `*** DETECT-REPEAT` |

**E 是这一轮的重点。** 如果没报，`trace` 行会告诉我们原因：

- `filtered=20` → Mission 不对（把 `MissionFilter` 改成 `2,7` 再试）
- `veh=1` 或 `2` → **插件是分帧下发的** → 这条路走不通，我会如实说明

### 阶段 D · 把日志发我

日志位置：`<游戏目录>\MsgLog\FairGuard_*.log`
（`E:` 盘我读得到，你说一声"测完了"就行。）

**重点回答三个问题**：
1. 阶段 B 有没有**误报**（不该出现的 `DETECT`）？
2. 阶段 C 的 E 有没有**报出来**？`veh` 是多少？
3. `trace` 行里出现最多的 `veh` 是几？（决定这条路走不走得通）

## 八、它和探针的关系

同一个 DLL 里两件事，共用同一个取样钩子（`0x64C38D` + `0x55D360`）：

| | 检测器 `[Detector]` | 探针 `[Probe]` |
|---|---|---|
| 目的 | 实时抓自动装车（**正式功能**） | 校准地址、诊断"为什么没数据" |
| 输出 | `DETECT` / `DETECT-REPEAT` / `trace` / `DETECT-SUMMARY` + 屏幕提示 | `evt` / `raw` / `list` / `BURST` 行 |
| 默认 | 开 | 开（日志量不大，留着便于排查） |

**为什么合成一个 DLL**：两者都要钩同样的两个地址。
Syringe 对**同一地址**的多次 hook 是后装覆盖先装 —— 两个 DLL 各钩一次必然冲突。

## 十、日志阅读工具：FairGuardReport

> 给**玩家**用的：把原始日志变成一份看得懂的 HTML 报告，同时**独立校验哈希链**。

### 10.1 怎么用

把 `FairGuardReport.exe` 和三个插件文件一起放进游戏根目录，然后**双击**：

- 自动找 `<游戏目录>\MsgLog\` 里**最新的一份** FairGuard 日志
- 生成 `<日志名>.report.html`，并自动用浏览器打开

也可以：**把某份日志拖到 exe 上**（只看那一份），或命令行
`FairGuardReport.exe <日志路径>`（加 `--no-open` 则只生成、不打开浏览器）。

### 10.2 报告里有什么

| 部分 | 内容 |
|---|---|
| **结论卡** | 哈希链校验结果（通过 / 第 N 条对不上 / 旧版本无法校验） |
| **概览** | 命中几次、涉及哪些房号、每次涉及几辆不同载具（veh 分布） |
| **判据是什么** | 一段话解释判定规则（给不看文档的人） |
| **怎么判断是不是误判** | 自查方法 + 已知盲区 |
| **命中明细** | 逐条：时间、帧、房号、单位数、不同载具数、链校验、chain |
| **运行配置** | 当时的 `[Detector]` 设置（换过配置也能对上） |
| **效力边界** | ⚠️ 免责声明（不能当判决书用） |

### 10.3 哈希链怎么校验（以及它到底能证明什么）

工具**不链接插件的任何代码** —— 只从日志文本里读 6 个字段
（房号、帧号、MM、units、veh、第几条），按同一套算法重算链，逐行比对。

**算法（1.3 起）**：

```
chain = SHA256( chain_prev || house || frame || MM || units || veh || 序号 )
chain 初值 = 32 个 0；日志里只打印前 8 字节
```

实现放在 `src/hashchain.h`，**插件与本工具 include 的是同一份** ——
物理上不可能对不上（"两边各抄一份"才是最大的坑，1.2 就是这么埋的雷）。

**它能证明什么**：

- ✅ 命中记录**没有被事后改动 / 删除 / 插入**（改一处，后面全崩）
- ❌ **不能**证明这份日志来自真实对局 —— 算法公开、无密钥，有人可以整份重造
- ❌ **不能**单独作为证据 —— 单人日志无法自证，需要**多方交叉核对**

> **任何人都能独立复现这个算法**：拿同样的 6 个字段 + SHA-256，
> 用 Python / PowerShell / 任何语言都能算。
> 本项目验证工具时就是用 **PowerShell 独立实现了一遍**，算出的链与工具一致
> （同时验证了"正确日志能通过""改一个数字能被抓出来"两条路径）。

### 10.4 旧版本日志

1.2 及更早的日志**无法校验** —— 那时的算法混进了日志里没有记录的数据
（时间戳、事件原始字节），谁都没法离线重算。
工具会识别版本并**明确说明"不是被篡改，只是不可校验"**，不会显示误导性的 ✗。

### 10.5 自检

```
FairGuardReport.exe --selftest
```

验证 SHA-256 实现（FIPS-180-4 标准向量）与链算法的确定性 ——
`src\build.bat` 每次构建都会跑它，不通过就不出产物。
