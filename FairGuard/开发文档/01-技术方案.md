## 一、为什么这条路走得通

《尤里的复仇》联机用 **lockstep（帧同步）**：所有玩家把操作打包成"命令"广播给每个人，
各客户端在**同一帧**执行同样的命令。

引擎把待执行的命令放在全局队列 `EventClass::DoList` 里。**每个客户端都有这个队列，
且里面装着所有玩家（含远程）的命令** —— 这就是数据源。

**探针只读这个队列**，不写任何游戏状态、不发任何事件、不改任何指令。
因此：

- **只需自己安装**，联机时对手不用装
- **不会造成不同步**（lockstep 同步的是指令序列，不是本地内存读取）
- **改 UI 也绕不过去**（数据是引擎即将消费的指令）

## 三、数据结构

### 3.1 `QueueClass`（队列布局）

来源：`YRpp/QueueClass.h`，并已用 `Execute_DoList` 的代码交叉验证。

```cpp
template<class T, int size>
class QueueClass {
public:
    int Count;          // +0x00
private:
    int Head;           // +0x04
    int Tail;           // +0x08
    T   Array[size];    // +0x0C   步长 sizeof(T)
    int Timings[size];  // Array 之后
};
```

**地址自校验**（判断"地址没错"的有力依据）：

```
Array   = 0x8B41F8 + 0x0C = 0x8B4204
Timings = 0x8B4204 + 16384*111 = 0xA70204
结束于   = 0xA70204 + 16384*4   = 0xA80204
而 0xA80208 是已知的 ParticleSystemClass::Array —— 严丝合缝
```

**⚠️ 这是环形队列**，元素下标不是 `i`：

```c
slot = (Head + i) & (16384 - 1);          // Head 在 0x8B41FC
element = 0x8B4204 + slot * 111;
```

来源（`Execute_DoList` 自己的代码）：

```
64c3ae:  03 c6                 add  %esi,%eax          ; Head + i
64c3b0:  25 ff 3f 00 00        and  $0x3fff,%eax       ; % 16384
64c3bb:  cmpb $0x1c,0x8b4204(%eax,%eax,2)             ; 0x8b4204 + eax*111
```

### 3.2 `EventClass`（单条事件，111 字节）

```cpp
class EventClass {          // sizeof == 111（有编译期断言）
    EventType    Type;         // +0   操作类型
    bool         IsExecuted;   // +1
    char         HouseIndex;   // +2   ★哪个玩家（-1 = 无效）
    unsigned int Frame;        // +3   ★该命令在第几帧执行
    union { char DataBuffer[104]; ... };  // +7
};
```

**⚠️ 头部（`+0..+6`）有编译期断言保证；`DataBuffer` 内部是本次实地校准出来的。**

### 3.3 `MegaMission` 的字段偏移（**已实地校准**）

`EventType::MegaMission = 0x04` 是最重要的类型（移动/攻击/进入都属于它）。
其 `DataBuffer` 布局（偏移为**相对事件起点**）：

| 偏移 | 字段 | 大小 | 说明 |
|---|---|---|---|
| `[7..11]` | `Whom` | 5 | 发令对象 `TargetClass`：ID(4) + RTTI(1) |
| **`[12]`** | **`Mission`** | **1** | **★ `02`=Move，`07`=Enter** |
| `[13]` | `_gap_` | 1 | |
| `[14..18]` | `Target` | 5 | 目标 |
| **`[19..23]`** | **`Destination`** | **5** | **★ 目的地（载具）** |
| `[24..28]` | `Follow` | 5 | |
| `[29]` | `IsPlanningEvent` | 1 | |

**校准方法**：用真实联机日志的原始字节，对照"手动装车(Enter) vs 自动装车(Move)"两组，
`[12]` 稳定给出 `02`/`07`，与 `Mission` 枚举吻合 → 偏移正确。
`[19..23]` 的取值在"进同一辆载具"时恒定、在"每个单位配一辆载具"时互不相同 → 偏移正确。

**样本文本**（同一条事件在两台机器上，头部完全一致）：

```
对手那台（字段完整）:
04 00 00 5C 57 00 00 | 6D 3E 10 00 34 | 02 | 06 | 00 00 00 00 00 | 1D DF 00 00 0B | 6D 3E 10 00 00 | 00 ...
 ↑  ↑  ↑  └───┬────┘   └─────┬──────┘   ↑    ↑    └─────┬──────┘   └──────┬──────┘
类型 执行 房号  Frame=22364   Whom(5B)  Mission gap   Target(空)      Destination
```

## 五、⚠️ 单机不产生 `EventClass`（重要）

**实测结论**：

| 场景 | `Execute_DoList` 调用 | `DoList.Count` |
|---|---|---|
| **单机** | 每帧调用（`calls == f`） | **每帧都是 0** |
| **联机** | 约 1/2 的帧调用 | **有值（实测最大 34）** |

反汇编印证：`Count <= 0` 时直接跳走

```
64c38d: mov 0x8b41f8,%edi      ← edi = DoList.Count
64c397: cmp %ebp,%edi
64c3a1: jle 0x64c40d           ← ★ Count 为 0 就直接返回
```

**原因**：那套事件队列是为**网络同步**而存在的。单机不需要同步，引擎直接执行命令，
不产生 `EventClass`。

**⇒ 单机测试永远拿不到数据，必须在联机环境验证。**

## 六、⚠️ 本机日志的事件字段不完整

同一条事件在两台机器上的记录：

```
本机:  ... 34 02 [00] 00 00 00 00 00 1D DF 00 00 0B 6D 3E 10 00 00 00 [5F 24]
对手:  ... 34 02 [06] 00 00 00 00 00 1D DF 00 00 0B 6D 3E 10 00 00 00 [00 00]
                 ↑偏移13 起不同
```

- **本机**：在事件**刚生成**的瞬间读（钩点 `0x64C38D`），`Destination` 等还没算出来
- **对手那台**：读到的是**同步完成后**的完整事件

**⇒ 分析必须用"对手那台"的日志** —— 也就是**探针装在旁观者位置时数据质量更好**。

（这也意味着：将来做"多方交叉取证"时，**只能对事件头部做哈希**，不能整条哈希。）

## 七、探针的实现要点

```
钩点 1: 0x64C38D (6 字节)  —— 主取样
        mov 0x8b41f8,%edi     ← 一条指令、绝对寻址、不碰栈
        时机: DoList 已就绪、事件即将被消费

钩点 2: 0x55D360 (5 字节)  —— 心跳 / 备用
        mov 0xa8e9a0,%al      ← ChatBox/AutoKit/Phobos/AutoLoad 同址，久经验证
        注意: 这个时刻 DoList 还是空的，不能单独用来取样

每个逻辑帧（靠 CurrentFrame 去重）:
  1. 按玩家分桶统计"本帧要执行"的事件（Frame == CurrentFrame 且未执行）
  2. 分类: ops(玩家操作) / chat(聊天) / proto(协议) / other
  3. 触发阈值时输出告警
```

**判据所需的数据**：同一帧内、同一房号的 `MegaMission` 事件集合，
从中提取每个事件的 `Whom`（[7..11]）与 `Destination`（[19..23]），
比较两者的**不同取值个数**。

## 八、⚠️ `Destination` 的语义随 `Mission` 变化（1.2 才发现的关键事实）

**在 1.1 之前，这份文档只写了"`Destination` = 目的地（载具）" ——
这句话只在 `Mission=7 (Enter)` 时成立。** 第二轮实测把这个坑挖了出来。

| Mission | 目标是什么 | `Destination` 表现 | 能否用于判据 |
|---|---|---|---|
| `2` Move | 一个**格子**（CellClass） | 普通移动时大家同格 → 1 个值；<br>**路径点模式下引擎为每个单位展开各自的目标格** → 20 个单位给出 10~14 个值 | ❌ **会误报** |
| `7` Enter | 一辆**载具**（对象本体） | 手动点同一辆车（不管框多少单位）→ 1 个值；<br>自动装车 10 单位配 10 辆 → 10 个值 | ✅ 判据只认它 |
| `0x0B` Area_Guard 等 | 未深究 | 实测里与 Move 类似地分散 | ❌ 不放行 |

**为什么之前没发现**：字段校准（1.0 阶段）用的是**手动装车**的样本，
那张实测表里的关键行全是 `07xN`（Enter）—— 结论本身没错，
错在**把它推广到了所有 MegaMission**。

**现在的处理**：
- 判据侧：`MissionFilter`（默认 `7`），见 `detector_core.h` 文件头
- 探针侧：`BURST` 行和 `evt` 行的 `MM=` 仍然统计**全部** MegaMission（那是诊断信息），
  只有判据受 `MissionFilter` 影响
- 回归测试：`case_pathway_move_false_positive()`

**还没搞清楚的**：`Destination` 的后 1 个字节是 RTTI（实测见过 `0x0B`、`0x34`），
含义未深究。判据只用前 4 字节 ID —— 目前不影响结论，但如果以后要区分
"目标是格子还是对象"，这个字节可能就是钥匙。
