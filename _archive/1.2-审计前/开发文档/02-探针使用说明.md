# 探针使用说明与诊断行速查

> 面向"要跑测试"的场景。原理看 `01-技术方案.md`。

---

## 一、部署

把这三个文件放进**游戏根目录**（`gamemd.exe` 所在目录）：

```
FairGuard.dll          <- 插件本体
FairGuard.dll.inj      <- 钩子声明（文件名必须与 DLL 完全一致，纯 ASCII）
FairGuard.ini          <- 配置（可选，缺省用默认值）
```

日志写在：

```
<游戏目录>\MsgLog\FairGuard_YYYY-MM-DD_HH-MM-SS.log
```

**两个已知的游戏目录**：

| 用途 | 路径 |
|---|---|
| 纯原版 | `E:\RA2\ModManager-v1.1.0.5\Mods\Yuri\Files\` |
| MO | `E:\RA2\Mental Omega\` |

**⚠️ 联机时两台机器都要装**（如果要对比双方视角）；只想看对手的话，装自己这边就够，
但**分析时优先用"没有操作的那台"的日志**（字段更完整，见 `01` 第六节）。

## 二、配置项（`FairGuard.ini`）

| 项 | 默认 | 说明 |
|---|---|---|
| `Enable` | `1` | 总开关。`0` = 完全不动，连日志都不写 |
| **`DumpRaw`** | `0` | **`1` = 输出每条事件的原始 hex**（校准字段时必需） |
| `DumpBytes` | `32` | 每条 dump 多少字节（8~111） |
| `BurstOps` | `5` | 单帧操作数达到它就告警（**先设 99 收基线**） |
| `LogEveryFrame` | `0` | 空帧也记一行（排查"探针是否在跑"时开） |
| `LogUtf8` | `0` | `0`=GBK，`1`=UTF-8 带 BOM |

## 三、日志行速查

### 3.1 启动头（每次进程启动一次）

```
FairGuard 1.0 start
config: Enable=1 DumpRaw=0 ...
addr: DoList=<008B41F8> OutList=<00A802C8> CurrentFrame=<00A8ED84>
read-only probe: does not modify any game state
```

### 3.2 活性与入口

```
hook: frame alive (0x55D360), CurrentFrame=0        ← 帧钩子被执行（只记一次）
hook: ExecuteEventsHook #1 entered, frame=0         ← 主钩子被执行（只记前 3 次）
```

### 3.3 每帧统计（只在有数据时输出）

```
evt f=22364 q=14 n=11 | h0 ops=10 chat=0 proto=0 MM=10 | h1 ops=0 chat=0 proto=1
    │       │  │        │  │              │             └ 另一玩家
    │       │  │        │  │              └ MegaMission 数量 ★检测重点
    │       │  │        │  └ 玩家操作数 ★
    │       │  │        └ 房号（哪个玩家）
    │       │  └ 本帧事件总数
    │       └ 队列当前总条数（含未来帧）
    └ 逻辑帧号
```

**分类含义**：

| 字段 | 含义 |
|---|---|
| `ops` | 玩家操作类（移动/生产/建造/修理/卖…） |
| `chat` | 聊天 |
| `proto` | 协议类（`FrameInfo` 等，**每玩家每帧都有，不是操作**） |
| `other` | 其余（非零时才显示） |
| `MM` | 其中 `MegaMission` 的数量 |

### 3.4 队列状态（每 60 帧一次，**不管有没有数据**）

```
list: f=1920 in=5/10 out=2/3 calls=959 maxOps=3@h0 | e0 t=1C h=1 fr=1920 ex=0
           │      │  │    │  │      │       │          │
           │      │  │    │  │      │       │          └ 首条事件: 类型/房号/目标帧/已执行
           │      │  │    │  │      │       └ 历史最高 ops 出现在哪个房号
           │      │  │    │  │      └ 单帧单玩家 ops 的历史最大值
           │      │  │    │  └ 钩子累计调用次数
           │      │  │    └ OutList 当前/历史最大
           │      │  └ DoList 当前/历史最大
           │      └ 同上（当前值/历史最大值）
           └ 帧号
```

**这一行是定位"哪一步没东西"的关键**：

| 现象 | 含义 |
|---|---|
| `calls` 不增长 | 钩子所在函数压根没被调用 |
| `calls` 增长但 `maxIn=0` | 队列一直是空的（**单机就是这样**，见 `01` 第五节） |
| `maxIn>0` 但没有 `evt` 行 | 帧号基准不对（曾因环形索引算错导致） |
| `maxOut>0` 而 `maxIn=0` | 事件只停在"本机待发" |

### 3.5 原始字节（`DumpRaw=1` 时每条一行）

```
raw f=22364 h=0 t=0x04 fr=22364 ex=0 | 04 00 00 5C 57 00 00 6D 3E 10 00 34 02 06 ...
                                        ↑  ↑  ↑  └────┬────┘ └─────┬──────┘ ↑  ↑
                                      类型 执行 房号   Frame=22364   Whom(5B)  Mission gap
```

**解析偏移**（相对事件起点）：`[0]`类型 `[1]`已执行 `[2]`房号 `[3..6]`帧号
`[7..11]`Whom `[12]`**Mission** `[13]`gap `[14..18]`Target `[19..23]`**Destination**

### 3.6 突发告警（探针层，**不是**判据）

```
*** BURST f=22364 h=0 ops=10  (MegaMission=10, Mission=7(Enter): 10)
```

单帧该房号的玩家操作数达到 `BurstOps`（默认 5）就记一行。
括号里是**该房号自己**的 `MegaMission` 数与其中 `Mission=07(Enter)` 的条数
（1.0 时代这里是全房号的总数和一个恒为 `-1` 的占位，1.1 已修正）。

> ⚠️ **`BURST` 不是判据**。它只看"命令条数多不多"，不看目的地，
> 所以正常玩家的批量操作也会触发。真正的判据是下面的 `DETECT` 行。

### 3.7 检测器告警（**这才是判据**）

```
*** DETECT f=26004 h=1 units=10 veh=10 MM=10 (Move=0 Enter=10) ratio=100% chain=1A2B3C4D5E6F7081
*** DETECT-REPEAT f=26548 h=1 hitsInWindow=2/600 frames, totalHits=2
detraw f=26004 h=1 i=0 | 04 00 01 94 65 00 00 6D 3E 10 00 34 07 06 ...
```

| 字段 | 含义 |
|---|---|
| `units=` | 这批命令涉及几个**不同**的发令单位 |
| `veh=` | 打给了几辆**不同**的载具 ← **判据的核心数字** |
| `MM=` | 本帧该房号的有效 `MegaMission` 条数 |
| `(Move= Enter= Other=)` | Mission 分布（`02`=Move，`07`=Enter） |
| `ratio=` | `veh / units` 的百分比（100% = 严格一对一） |
| `chain=` | 哈希链当前值前 8 字节 |
| `invalid=` | 字段还没算出来（值为 0）的条数，不参与判据 |
| `[repeated]` | 本帧同时升级为"重复命中" |
| `detraw` | 仅在 `[Detector] LogRaw=1` 时输出，命中批次的原始字节（每条 24 字节） |

**每 1800 帧**（有新命中时）和**退出游戏时**还有汇总：

```
[DETECT] alive f=24000 hits=2 scans=812 frames=24000 chain=1A2B3C4D byHouse=h1:2 recs=2
[DETECT-SUMMARY] ver=1.1 f=74000 hits=2 scans=1904 firstHit=26004 lastHit=26548 byHouse=h1:2 chain=<完整64位> recs=2
```

`scans=` 是"出现过有效命令的帧数"，**它不涨说明根本没有数据**（比如单机）。

**未命中帧的诊断行**（`[Detector] TraceAll=1` 时，规模达标但没命中的帧也记一行）：

```
trace f=13823 h=0 units=0 veh=0 MM=0 (Move=0 Enter=0 Other=20) ratio=0% filtered=20
```

它是回答"**为什么没报**"的唯一第一手材料：`filtered=` 大说明 Mission 不在
`MissionFilter` 里；`veh=1` 说明目的地不够分散（可能真是手动操作，或者插件分帧下发）。

完整说明见 **`07-检测器使用说明.md`**。

## 四、测试流程

> 探针的取样三步（阶段 1/2/3）已经做完，结论见 `01` 与 `03`。
> **现在要测的是检测器** —— 步骤见 `07-检测器使用说明.md` 第七节。
> 下面是探针自身的排查流程，地址出问题时才需要重跑。

### 阶段 1：确认探针活着（单机即可）

1. 部署三个文件，启动游戏
2. 日志里应出现 `start` + `addr` + `hook: frame alive`
3. 单机时 `list:` 行会显示 `in=0/0`（**正常**，单机不产生事件）

### 阶段 2：联机取样（**必须联机**）

1. 两台机器都装探针（或只装自己这边 + 让对手无操作）
2. **约好时间点**做特定动作（例：第 2 分钟按三次 Ctrl+D）
3. 退出后把 `MsgLog` 下的日志取出来

### 阶段 3：字段校准（需要 `DumpRaw=1`）

分开做、**间隔 10 秒以上**，便于按时间切分：

| 编号 | 动作 |
|---|---|
| A | 手动框选 5 个兵 → 点**一辆**运输车 |
| B | 按 Ctrl+D 用 AutoLoad 装 5 个兵 |
| C | 手动框选 5 个兵 → 再点一次运输车 |

对比三组事件的原始字节：`Mission` 应为 `07`/`02`，`Destination` 唯一值应体现
"几辆载具"。
